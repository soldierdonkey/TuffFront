# OpenFront userscripts – testing notes

## Project
- Source is split into `src/` (features), `config/*.json` and `styles/*.css`; `npm run build` bundles them into `dist/openfront-demo.user.js`, the file to test and install. See `README.md` for the layout. Edit the sources, never `dist/`.
- `openfront-demo.user.js` below means the built `dist/openfront-demo.user.js`. It shows a bottom-center button: "Script loaded" on the menu, "Game detected" in a game.
- `install.js` / `package.json`: builds, then installs (`npm run install-script`).

## Detecting a game (DOM scraping)
- The client toggles `in-game` on `<body>` while a game runs (`OpenFrontIO/src/client/Main.ts:311`). This is the primary signal.
- Fallbacks: URL path `/<worker>/game/<id>` and a visible `<game-left-sidebar>`.
- Game UI custom elements (`control-panel`, `events-display`, `build-menu`, `game-left-sidebar`, ...) exist in the DOM on the menu too, but are hidden. Check visibility, not just presence.
- In a solo game the left/right sidebars and canvas became visible, but `control-panel`, `events-display` and `build-menu` stayed hidden during the spawn-selection phase. Don't use them as the signal.
- In the headless solo run the URL stayed `/`, while a visible Chrome run showed `/w11/game/<id>`. Don't rely on the URL alone.

## Reading game state without the server
How the data flows (from `~/Desktop/OpenFrontIO`; the game simulation runs on every client, the server only relays intents):
- Simulation runs in a web worker (~10 Hz) -> `GameView` (`src/client/view/GameView.ts`) is the client-side mirror -> the WebGL renderer draws it. Everything the script needs is already in the page's memory, so reading it costs the game server nothing.
- The map is drawn on a WebGL canvas, so territory and borders are NOT in the DOM. There is nothing to scrape from the map itself; read the objects below instead.
- Where to get the objects: in a game, HUD custom elements (`src/client/hud/layers/*.ts`) hold them as JS properties (Lit `@property`). Reachable through `document.querySelector(...)` because the userscript runs with `@grant none`, i.e. in the page context.
  - `game-left-sidebar`.game (also `control-panel`, `player-info-overlay`): the `GameView`.
  - `build-menu`.transformHandler (also `emoji-table`, `chat-modal`, `onboarding-overlay`): the camera.
  - Both appear a few seconds after `in-game` is set on `<body>`; null-check them.
- `GameView` (sync, local): `myPlayer()`, `players()`, `playerBySmallID(id)` (returns a `PlayerView` or terra nullius, check `.isPlayer()`), `ownerID(tile)` (0 = nobody), `forEachNeighbor(tile, cb)`, `ref(x,y)`, `x(tile)`, `y(tile)`, `width()`, `height()`, `isLand(tile)`, `inSpawnPhase()`, `ticks()`.
- `PlayerView` (sync, local): `smallID()`, `name()`, `type()` (`'BOT' | 'HUMAN' | 'NATION'`), `numTilesOwned()`, `isAlive()`, `hasSpawned()`, `allies()`.
- A "tribe" in the UI is `PlayerType.Bot`. Nations are `'NATION'` (AI with diplomacy), humans are `'HUMAN'`.
- `PlayerView.borderTiles()` returns a Promise: it is a request to the local worker, NOT the game server (`game.worker.playerBorderTiles`). Fine once a second; don't call it per frame. There is no ready-made "neighbours" API: derive bordering players from `forEachNeighbor` + `ownerID` over those border tiles (this is what the game's own `TutorialPanel.refreshBordering` does).
- Camera: `transformHandler.worldToScreenCoordinates({x,y})` returns client (viewport) coordinates; `scale`, `offsetX`, `offsetY` are the pan/zoom. It reads a cached bounding rect, so it is stale only after a canvas resize.
- Avoid anything that hits the network: profile calls (`PlayerView.profile()`), the API, or the lobby/server list. The tribe attack guide in the script uses only the calls above.
- Drawing on the map: the script paints the tribe's border tiles onto a map-sized offscreen canvas, then stretches it over a `position:fixed`, `pointer-events:none` overlay canvas using the two projected map corners each animation frame.
- Verified on the local dev server only, not on live openfront.io (live may run a different build than the `~/Desktop/OpenFrontIO` source). If live differs, the first thing to check is whether those element properties still exist.

### Tribe attack guide (bot-phase expansion, annexation planner)
- Goal: maximise land annexed. A tribe is annexed for free once every neighbour of its land is us (`PlayerExecution.surroundedBySamePlayer`: no free land, no ocean shore, not on the map edge). So the script tells you which enclosed tribes ("pockets") to LEAVE alone and which neighbours to attack. It ports the engine's own planner (`OpenFrontIO/packages/engine/src/execution/nation/BotAnnexation.ts`, `planBotAttacks`/`BotScanner`) and adds boat entrances and a finishing-move bonus.
- Pipeline, every 1 s in `refreshTribe`: `scanTribes` (ring 1 = tribes bordering us, ring 2 = tribes bordering those; ring 2 cached 3 s; `borderTiles()` is a local worker call) -> `planAnnexations` (pure, no DOM) -> `plan` -> `evaluateTribes`/`drawAnnotations` every frame (clicks follow the attack slider live).
- `planAnnexations`: classify (walled / pocket / boat pocket) -> `chooseKept` (max-weight independent set over pockets, weight = tiles, exact up to 16 pockets else greedy, 30 pocket cap, +10% stickiness for last tick's kept set) -> rank ring-1 attack targets by `(tiles + sum of tiles(K)/remaining(K) for each kept pocket K it walls in) / cost%` (the attack that finishes a pocket gets the whole pocket) -> number targets `#1..` while their cost stays within 90% of our troops (the first is always shown). If nothing else borders us, the best kept pocket without an entrance is attacked instead.
- Boat pockets: a closed tribe with 1-6 ocean-shore tiles (`isOceanShore`) and us owning some ocean shore (a global check, not distance) is a pocket whose entrance must be landed on (counts as one more remaining step). If an entrance tile already touches our land the chip says ENTRANCE instead of BOAT IN. Entrance tiles are painted magenta (5x5) on the map layer; the best target outline stays green (3x3).
- Chips (under the troop count): `ANNEX · 1 click` (walled in), `LEAVE · annexed after N more` (kept, bordering), `ANNEX LATER · N left` (kept, behind the front, dim), `BOAT IN · N tiles` / `BOAT IN · last step` (magenta), `#k · cost` (planned attack order), and for the rest `WEAK/BUSY/COSTLY/SKIP`. Cost is clicks, but COSTLY/SKIP and costly targets show `N% troops` (2x the tribe's troops over ours). ★ marks the best target (largest ANNEX, else `#1`), which also gets the green outline.
- Clicks: each click sends `attackRatio * remaining troops` (see `PlayerActionHandler`), aiming for 2x the tribe's current troops, so the count simulates the drain. The ratio is read live from `control-panel`.uiState.attackRatio (fallback: localStorage `settings.attackRatio`, default 0.2).
- Name plate geometry: the plate is WebGL, so chips are drawn on the overlay canvas, mirroring `name.vert.glsl` / `render-settings.json` (nameScaleFactor 0.4, cap 3, troop size 0.6, font base/size 36/48, troop line centre 1.1 lines below `nameLocation()`). Chips hide when the game culls the plate (line height < cullThreshold * canvas width / 2). If those constants change, update `NAME_*`/`TROOP_SIZE`/`CULL_THRESHOLD`.
- Unverified in actual play: that an attack on a walled-in tribe annexes it (only the engine's comment says so), that landing on a small entrance then annexes the pocket (inferred from `surroundedBySamePlayer`; the engine planner treats any coast as open and has no boat logic), and whether a boat can really reach a given inlet. No natural walled-in tribe exists at spawn.
- Not implemented from the guide: ocean connection, blocking off enemy players, city build timings.

### Testing the tribe highlight
- Planner unit tests need no browser: read the script in node, append `globalThis.__t = { planAnnexations, chooseKept, chipFor }` before the final `})();`, and run it in a `vm` context with stub `document`/`window`/`localStorage`/`setInterval`/`requestAnimationFrame`/`MutationObserver`. Build tiny node lists by hand (see the cases: pocket surrounded by four tribes, touching pockets, unaffordable neighbour, finishing move, boat entrance sizes, budget) and compare `chooseKept` with brute force on random graphs.
- In-game test copy: append `window.__t = { scanTribes, planAnnexations, paintLayer, getPlan, setPlan, ... }` before the final `})();`. To force a plan, call `setPlan` (and stop the refresh by setting `refreshing = true` through a hook) so the 1s refresh does not overwrite it. Check `scanTribes` ring 1 against a full-map scan of tiles owned by `myPlayer()`.
- It needs a spawn within ~3 tiles of a bot's territory: find unowned land next to a bot tile, set `transformHandler.offsetX/Y` to center it, then click the projected screen position. At >=5 tiles the spawn has no bordering player, which exercises the do-nothing case.
- Verify against ground truth: scan every tile owned by `myPlayer()` with `forEachNeighbor` and compare the set of neighbouring owners with what the script picked.
- The page error `keyboard.addEventListener is not a function` in headless Chrome is harmless. Extra GL flags (`--use-angle=swiftshader`) broke game start; use the plain launch.

## Testing against live openfront.io
- Headless Chrome (`headless: 'new'`) is stuck on a Cloudflare "Performing security verification" page. The DOM is empty of the app.
- A visible Chrome (`headless: false`, `ignoreDefaultArgs: ['--enable-automation']`) passes the check after ~10s. Wait before inspecting.
- Live pages show real ads (video ad bottom-left, side banners). A user mentioned an adblock popup can appear; none appeared in the test browsers because they have no adblocker.

## Testing against the local offline dev server (preferred)
- Repo: `~/Desktop/OpenFrontIO` (node_modules already installed).
- Start: `npm run dev` there. Client at http://localhost:9001/ (Vite + dev game server). No Cloudflare check, and headless Chrome works.
- Expect harmless warnings: "Error getting cosmetics" and "Server list API still unreachable, treating as offline".
- Solo games work offline: click the `SOLO` button, then the last `START GAME` button inside `single-player-modal`.
- The dev server keeps running after tests. Stop it manually (Ctrl+C or kill the `npm run dev` process). `pkill` was denied by the permission classifier in a past session.

## Puppeteer setup
- Use `puppeteer-core` with `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome` (no bundled Chromium; system chromium not installed).
- Install it in the scratchpad dir, not in the project.
- Inject the userscript for tests by `page.evaluate(fs.readFileSync('dist/openfront-demo.user.js','utf8'))` after the page loads (~6s). Tampermonkey's `@run-at document-end` is not emulated.
- Verified results: menu → "SCRIPT LOADED"; after solo START GAME → "GAME DETECTED".

## Constraints and compliance (keep true for every change)
Audited on 2026-10-30 against `openfront-demo.user.js` v0.6.0 by grepping for network, input and write calls.
- Frontend only: `@grant none`, no `fetch`/`XMLHttpRequest`/`WebSocket`/`sendBeacon`/`GM_*`, no `@connect`. The script makes no requests of its own and has no server component.
- Separate from the servers: the only data source is page memory (`GameView`, `PlayerView`, `transformHandler`, `control-panel.uiState`). `borderTiles()` goes to the local web worker (`WorkerClient.playerBorderTiles` -> `GameRunner`), not the game server. Never call `profile()`, the API or the lobby list.
- Warning panel + notification feed (added 2026-10-30, untested in a browser): `#of-demo-warnings` sits where the "Choose a starting location" banner is (`heads-up-message`, top 15%, under it while it shows). Systems are independent entries in `WARNING_SYSTEMS` (`nukes`, `landings`, `mirvAccess`, `hydrogenFirst`; the last two read every player's gold and silos from client state); switch one off with `config.warnings = { nukes: false }` in the localStorage key. They read `game.units()` (`targetTile()`, `owner()`). The built-in `events-display` is moved under the panel with an injected `<style>` (`#of-demo-feed-style`, partly transparent) and long player names in its rows are shortened keeping `[CLAN]` (`fitName`). This is the one place the script touches game DOM: it rewrites the text node and `title` of feed rows (restored when the script is disabled). The alliance popups (`actionable-events`) get the same style and stack between the panel and the feed; clicking a card (outside its Accept/Reject/Focus row) hides it, and `config.popupSeconds` (Alt+click the indicator, 0 = game timing) hides them after N seconds. Hiding is a CSS class (`of-dismissed`) on the card, keyed by its text; the game's own state is untouched. It still sends nothing and dispatches no events. Unit type strings (`'MIRV'`, `'Hydrogen Bomb'`, `'Atom Bomb'`, `'MIRV Warhead'`, `'Transport'`) and `targetTile()` on transports are read from the source, not verified in play.
- Read-only toward the game: it never assigns to game objects, never sends intents, never dispatches synthetic mouse/keyboard/pointer events and never calls `.click()` on game UI. Its only DOM writes are its own indicator button, style tags, warning panel and a `pointer-events:none` overlay canvas, plus the feed-row text/title described above. Its only storage is its own localStorage key (`of-demo-userscript-config`); it reads `settings.attackRatio`.
- Risky-move confirmation (`src/features/risky-moves.js`, added 2026-10-30, untested in a browser): a capture-phase `pointerup` listener on `window` swallows (`stopImmediatePropagation`) a plain left map click when `troops * (1 - attackRatio) / peak troops of the last peakSeconds` is below the reserve for who borders us (40% neighbour >= 2x our tiles, 30% >= 1.5x, 20% other non-allied neighbour, 10% no player neighbour; `config/risky-moves.json`). It takes 3 clicks within `confirmSeconds` each: attempt (swallowed, shows a CONFIRM box just above the cursor, `pointer-events:none`), a click inside that box (always swallowed, arms the owner), then a click on the same owner, which passes through untouched. It never re-dispatches or synthesises a click. Not covered: keybinds (G), radial menu, touch, `leftClickOpensMenu`. Switch off with `config.riskyMoves = false`. This is the only place the script interferes with game input.
- No automation: the user decides and clicks every attack. The script only displays information (chips, outlines). Do not add auto-attack, auto-click, auto-expand, macros or timed input; that would break this rule.
- Detection (checked in `~/Desktop/OpenFrontIO` source, 2026-10-30): no client code looks for userscripts or foreign DOM. No `navigator.webdriver`, `document.scripts`, script-tag or `outerHTML` inspection, no Tampermonkey/userscript strings. The only `MutationObserver`s are in `src/client/HomepagePromos.ts` and watch the ad container. The server-side anti-cheat (`SocketIngress.ts`, `GameServer.ts` winner-vote replay check, `IntentAuthorization.ts`) validates intents and desynced results; a read-only script that sends nothing triggers none of it. Still, this is only the open-source code: the live site also loads Turnstile and third-party ad/analytics scripts, which could fingerprint the page, and the live build may differ. Nothing is hidden (known ids on the overlay canvas and button). Do not add evasion or spoofing code.
- **ToS VIOLATION (`resources/public/terms-of-service.html`, section 6.5, last updated 10/24/2026):** This technically violates the ToS. Users are aware of this and keep its use moral and do not use it in competitive contexts.
